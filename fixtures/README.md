# Synthetic fixtures

Generated by [`scripts/make_fixtures.py`](../scripts/make_fixtures.py). **None of these
numbers were measured.** They are modelled so every parser and check can run in CI without
GPUs, in the same file layout that `bcp collect` writes on a real node.

| Folder | Models | Expected verdict |
|---|---|---|
| `hgx-h100/` | 8x H100 SXM HGX node, NVLink 4 | pass |
| `dgx-b200/` | DGX B200 (8x B200 on an HGX baseboard, DGX OS release file present) | pass |
| `gb200-nvl72/` | One GB200 NVL72 compute tray: 4 GPUs, NVLink fabric joined to a rack-wide domain, host copies over NVLink-C2C | pass |
| `dgx-b200-degraded/` | DGX B200 with 2 of GPU5's 18 NVLinks down: NV16 in the topology, a DCGM failure, lower collective bandwidth | fail |

Formats imitated: `nvidia-smi --query-gpu` CSV, `nvidia-smi topo -m` (tab-separated, with
legend), the relevant parts of `nvidia-smi -q` (Product Architecture and Fabric sections),
nccl-tests tables, nvbandwidth matrices with `SUM` lines, and DCGM 4.x `dcgmi diag -j` JSON.
The DCGM parser walks the JSON for `name`/`results`/`status` rather than relying on exact
keys, because that schema changes between DCGM releases.

Regenerate after changing the generator, and CI checks they match:

```bash
python scripts/make_fixtures.py          # rewrite
python scripts/make_fixtures.py --check  # verify
```

When you have real output from `bcp collect`, add it as a new folder here too (after removing
serials, UUIDs and hostnames). Real fixtures catch parser drift that synthetic ones can't.
